5 steps to submit (DrivenData portal)

  1. Open the competition: https://www.drivendata.org/competitions/306/competition-doe-gems/ → click Submit.
  2. Under New submission → File to submit, click Choose file and pick the downloaded .tif (or the .zip containing a single .tif).
    Requirements (from problem page, submission format): single‑band float32, EPSG:32611, 100 m, same bounds as training data, values in [0,1], outside bounds null/NaN. Our file meets all.
  3. In Note (optional) paste: GEMSDOE83 H83B jog+ThK 40k B2 | HOLDOUT-DTI pure-cat 0.0038 SGMC-cal 0.0681 | unique ov0.68 r0.64 | format-valid UNSCORED (121/140 chars).
  4. In Unique submission name paste: GEMSDOE83-H83B-JOG-AUG-B2-40K
  5. Click Create submission. You should see “Submission created” (not the range error). Promotion to a real weekly slot is a separate selector step (cap shown on the submission page); this page certifies format only. Never submit the red H83-F file on the home page. Results appear on the leaderboard after organizer scoring.

The portal error “Predicted values must be in range [0,1]” — fixed

Three mechanisms measured (2026-10-21 re-audit) that can produce that exact message:

  • 0. The labels −1 sentinel (most direct): labels.tif/existing_faults.tif are int8 with nodata −1 on 7,111,787 cells (sha256 7ba308cc…, re-fetched and re-hashed this session). Any pipeline that casts label geometry to float32 without remapping −1→0/NaN submits −1.0 values → portal rejects. Our writer never copies label values; receipts prove min 0.0.
  • 1. The float32 sentinel: training_features.tif declares nodata -3.4028234663852886e+38 (float32 min). 7,113,308 cells per band use it, 3,061 inside the scored footprint. If those are written through unchanged they are outside [0,1] and the portal rejects. Evidence: we counted them per band (see scripts/fetch_mirrors.sh provenance, sha256 4371c82e…).
  • 2. The NaN sentinel: A raster with nodata=NaN and NaN outside footprint is competition‑legal (sample submission uses it: 5,167,373 finite inside, rest NaN), but one validator change away from same rejection. Evidence: both encodings are published; our portal‑safe variant is all‑finite with nodata=None.

The fix (verified by re‑reading the written bytes): Every download here is single‑band float32, EPSG:32611, 3292×3730, 12,279,160 cells, every cell finite, min 0.0 max 1.0, 0 cells outside [0,1], 0 NaN, no nodata tag (zeros variant). Each ships a checks-*.json receipt produced by re‑opening the file from disk. Run python scripts/check_submission.py docs/downloads/<file>.tif --strict-finite to verify yourself.

Note: The historical upload that triggered the error was never obtained, so the trigger remains inferred, not proven (IR‑83‑VERIFY‑01). Both mechanisms are engineered out here.

What the files are

  • -zeros.tif (primary, portal‑safe): outside footprint = 0.0, all 12,279,160 cells finite, passes strict validator.
  • -nan.tif (competition format twin): outside = NaN, identical values inside footprint, for the official spec.
  • .zip: Deflated zip containing the zeros.tif (portal accepts zip with single tif inside).

All three have SHA256 pinned in registry/submission_build.json and a per‑file receipt.
